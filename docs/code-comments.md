# Комментарии и JSDoc

Правила для всех файлов проекта: `.ts`, `.tsx`, скрипты сборки, тесты.

---

## Принцип

Код должен читаться без комментариев. Хорошие имена и прозрачные структуры лучше любого пояснения. Комментарий нужен только там, где код уже максимально ясен, но контекст (*почему* так) неочевиден.

> Если колеблешься — **не пиши**. Лучше переименовать, чем объяснять.

---

## Когда писать

**Пиши, если:**

- Имя не раскрывает семантику, а переименовать нельзя (CSS custom property, публичный контракт, внешний API).
- Есть неочевидный инвариант или порядок, который можно случайно сломать (`// порядок важен: X зависит от Y`).
- Есть отсылка к внешнему источнику: спецификации, архитектурному решению, ссылке на обсуждение.
- Нужно сгруппировать большую структуру в визуальные секции (sectioning).

**Не пиши, если:**

- Комментарий повторяет имя идентификатора: `// массив цветов` над `const colors`.
- Он ссылается на текущий PR, задачу, автора, тикет, issue — эта информация живёт в git log и PR-описании.
- Он описывает WHAT делает код — переименуй переменную или разбей функцию.
- Это TODO / FIXME без автора и тикета.

## JSDoc

### Обязательно

JSDoc пишется на всём, что **экспортируется и потребляется за пределами файла**:

- публичные типы и интерфейсы,
- публичные функции, константы, хуки, компоненты, утилиты,
- экспортируемые значения, которые попадают в чужой тулинг (registry JSON, CLI конфиг и т.п.).

Если значение используется только внутри файла — JSDoc не нужен.

### Стиль

- **Одна строка** для простых случаев: `/** Короткое описание. */`
- **Многострочно** только если без `@param` / `@returns` / `@example` смысл не передать.
- **Не пиши теги, повторяющие типы.** `@param name {string} имя` избыточно, тип уже в сигнатуре.
- **Точка в конце** короткого описания.

### Примеры

**Хорошо:**

```ts
/** Имена осей контракта (включая base). */
export type TokenContract = keyof typeof TOKEN_CONTRACT

/**
 * Объединяет CSS-классы, отбрасывая falsy.
 *
 * @example cn(styles.root, disabled && styles.disabled, className)
 */
export function cn(...inputs: (string | false | null | undefined)[]): string
```

**Плохо:**

```ts
/**
 * @param {string[]} names — массив имён.
 * @returns {string[]} массив CSS-переменных.
 */
function toVars(names: string[]): string[]
```

Типы уже видны в сигнатуре, теги ничего не добавляют.

## Inline-комментарии (`//`)

### Секционные маркеры

Для больших структур используй два уровня:

```ts
// ── Верхний уровень (внутри ключа/файла) ────────────────────────

// Подгруппа внутри секции
```

- **Длинный маркер** `// ── Name ──────────────────────` — для секций верхнего уровня внутри одного блока (ключа контракта, тела функции, корня файла). Длина тире ~50–60 символов, на глаз одинаковая в соседних секциях.
- **Короткий маркер** `// Name` — для подгрупп внутри длинной секции.
- Символ разделителя — `─` (U+2500 box drawing), **не** обычный дефис.

### Поясняющие комментарии справа от строки

Разрешены, когда имя не раскрывает семантику:

```ts
"--surface-default",   // фон страницы
"--surface-paper",     // фон карточки / модалки / меню
```

**Запрещены**, когда имя самодостаточно:

```ts
"--color-primary-500", // ❌ основной primary-500 — и так ясно
```

Выравнивай колонку комментариев в одном блоке для читаемости.

### Файловый заголовок

Разрешено начинать файл многострочным `/** */` комментарием с правилами или глобальным контекстом — это не JSDoc-для-экспорта, а «@fileoverview» стиль:

```ts
/**
 * Контракт дизайн-токенов.
 *
 * Правила:
 * 1. Каждый пресет оси ОБЯЗАН определить ВСЕ переменные из своей секции.
 * ...
 */
```

Используй **только** если в файле есть глобальный инвариант, не выраженный в типах. Для обычного модуля заголовочный комментарий не нужен.

## Язык

- **Комментарии и JSDoc — на русском.**
- **Идентификаторы — на английском.**
- Устоявшиеся индустриальные термины (semantic, heading, body, elevation, spacing, surface, overlay, ...) пишутся по-английски даже внутри русского комментария:

```ts
// ── Semantic surfaces (меняются между light/dark) ───────────
```

Переводить термин только если его русский эквивалент в команде однозначен и не порождает путаницы.

---

## Что делать, если не уверен

1. Попробуй переименовать — комментарий чаще всего лишний.
2. Если не получилось — пиши *почему*, не *что*.
3. Если всё ещё не уверен — **не пиши**. Следующий читатель дополнит при необходимости.
